    Tienes el control total. Tú eres el usuario postgres

    ¿Quieres una base de datos Postgres sin restricciones? La tienes. Sin pseudousuarios limitados: obtienes el usuario postgres (el usuario de máximos privilegios, el usuario “root”). Es tuyo. Sin letra pequeña.

    StackGres es una solución Postgres completa, que integra varios componentes con configuraciones ajustadas por expertos.

    Para usuarios avanzados de Postgres, permite personalizar aún más los componentes y las configuraciones. Las configuraciones se validan por completo; no son un simple ConfigMap que puede romper tu clúster si lo configuras mal. Mira por ejemplo cómo ajustar las configuraciones de Postgres o Connection Pool. En cuanto a Kubernetes, puedes personalizar los servicios expuestos, las etiquetas del pod y las tolerancias de nodos, entre muchas otras cosas.

    Failover automático y alta disponibilidad con Patroni

    StackGres integra el software de alta disponibilidad para Postgres más reconocido y probado en producción: Patroni.

    Está totalmente integrado, no hay nada más que hacer. Si falla cualquier pod, cualquier nodo, cualquier cosa, en cuestión de segundos el clúster se recuperará automáticamente, sin intervención humana.

    StackGres expone para las aplicaciones una conexión de lectura-escritura (que siempre apunta al primario) y otra de solo lectura (un balanceador que distribuye la carga entre las réplicas), que se actualizarán automáticamente tras cualquier evento disruptivo.

    Copias de seguridad automatizadas, gestión del ciclo de vida

    Las copias de seguridad son una parte crítica de una base de datos, y son clave en cualquier estrategia de recuperación ante desastres. StackGres incluye copias de seguridad basadas en archivado continuo, que permiten recuperación sin pérdida de datos y PITR (restaurar una base de datos a un instante arbitrario del pasado).

    StackGres también proporciona gestión automatizada del ciclo de vida de las copias. Y las copias se almacenan siempre en el medio más duradero disponible hoy: object storage en la nube como Amazon’s S3, Google Cloud Storage o Azure Blob. Si trabajas on-prem, puedes usar Minio u otro software compatible con S3 para almacenar tus copias.

    Solo tienes que proporcionar los datos de acceso y credenciales de tu bucket y configurar la ventana de retención; todo lo demás es totalmente transparente y automatizado. También puedes crear copias manuales con un simple fichero YAML en cualquier momento.

    Logs distribuidos para Postgres y Patroni

    ¿Cansado de hacer kubectl exec en cada uno de los N pods de tu clúster, para luego hacer grep+awk sobre los logs de Postgres en busca de la información que necesitas? Con StackGres hay una forma mejor.

    ¡Consulta los logs con SQL, desde una ubicación centralizada! StackGres soporta logs centralizados y distribuidos. Con un simple CRD en YAML, o desde la consola web, puedes crear un clúster de logs distribuidos en segundos. Después, referéncialo desde el clúster o clústeres que crees.

    Los logs de Postgres y de Patroni se capturan mediante un sidecar de FluentBit, que los reenvía al servidor de logs distribuidos. Este contiene a su vez un colector Fluentd que ¡reenvía los logs a una base de datos Postgres dedicada! Para soportar la ingesta de grandes volúmenes de logs, esta base de datos dedicada se potencia con la gran extensión TimescaleDB (versión open source), en la que StackGres también se apoya para aplicar políticas de retención de logs.

    Consulta tus logs con SQL para liberar todo el potencial de DBA. O visualízalos en la consola web, que incluye capacidades de búsqueda y filtrado. Todos los logs se enriquecen con metadatos muy completos. Resolución de problemas de Postgres: te tenemos cubierto.

    CRDs de gestión de alto nivel. Listo para GitOps

    No necesitas instalar ningún cliente ni herramienta adicional para gestionar StackGres. StackGres está completamente dirigido por CRDs (consulta la referencia de CRDs). Tus peticiones se codifican en la sección spec de los CRDs, y cualquier información de resultado se proporciona en la sección status de los CRDs.

    Además, los CRDs están diseñados para ser de muy alto nivel y abstraer (ocultar) todas las complejidades de Postgres. Con StackGres, si conoces kubectl y los CRDs, también te has convertido en un experto en Postgres.

    Que los CRDs sean la interfaz de StackGres, sin requerir ninguna herramienta externa, te permite tener todos tus clústeres de Postgres codificados como IaC (infraestructura como código), y potencialmente versionados en Git. Esto habilita además GitOps, donde tus clústeres pueden gestionarse automáticamente cuando haces commit de cambios en los CRDs del repositorio Git.

    Y si prefieres una interfaz visual a los ficheros YAML y la línea de comandos, cada acción que puedes consultar o realizar con los CRDs también puede realizarse desde la consola web. Del mismo modo, cualquier acción realizada desde la consola web se reflejará automáticamente en los CRDs. Tú eliges.

    Connection pooling integrado del lado del servidor

    Debido al modelo de procesos de Postgres, es muy recomendable tener connection pooling en la mayoría de los escenarios de producción. Pero no es un tema sencillo.

    StackGres viene por defecto con connection pooling integrado del lado del servidor. Se despliega como un sidecar del contenedor de Postgres. El pooling del lado del servidor permite controlar el fan-in de conexiones, es decir, las conexiones entrantes a Postgres, y asegurar que Postgres no se vea desbordado por un tráfico que podría causar una degradación significativa del rendimiento.

    Puedes ajustar la configuración de bajo nivel o incluso deshabilitar por completo el connection pooling (mira el CRD PoolConfig), y por supuesto gestionarlo desde la consola web.

    StackGres también exporta métricas relevantes del connection pooling a Prometheus, y se muestran paneles especializados en el Grafana integrado en la consola web.

    Observabilidad mejorada mediante el filtro Postgres de Envoy Proxy

    El equipo de StackGres desarrolló, en colaboración con la comunidad de Envoy, el primer filtro Postgres para Envoy. Saber más

    Este filtro Postgres de Envoy proporciona observabilidad mejorada decodificando el protocolo de red de Postgres y enviando métricas a Prometheus. No solo se añaden métricas que no están disponibles a nivel de Postgres, sino que además tienen impacto cero en Postgres: se recogen a nivel del proxy, y este proceso es totalmente transparente para Postgres.

    StackGres utiliza un sidecar de Envoy para hacer proxy de todo el tráfico de Postgres de forma transparente. Así que no hay nada que hacer: mientras tengas Prometheus en tu Kubernetes, Envoy enviará métricas adicionales. Y la consola web de StackGres ya incluye paneles de Grafana integrados para visualizar estas métricas.

    Ajustado por expertos por defecto

    En StackGres estamos obsesionados con ajustar Postgres adecuadamente. Tanto que hemos creado postgresqlCO.NF, un sitio web que ayuda a cientos de miles de usuarios de Postgres a ajustar mejor su base de datos.

    Los clústeres de StackGres se crean con una configuración inicial de Postgres cuidadosamente ajustada, curada por nuestro equipo de DBAs expertos en Postgres. Si no eres un usuario avanzado de Postgres, esta configuración por defecto te cubrirá de sobra. Si prefieres ajustarla tú mismo, puedes crear uno o más CRD PostgresConfig y referenciarlos desde tu clúster o clústeres.

    Con StackGres, no necesitas ser un experto en Postgres para operar clústeres listos para producción.

UBI8 es de uso gratuito, y Red Hat la soporta plenamente si tienes un contrato de soporte de RHEL.
